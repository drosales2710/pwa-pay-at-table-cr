How the app works today

Four portals share one React tree via GuestProvider in App.tsx: guest PWA, server floor, kitchen/bar KDS + cashier, and admin. Mutations (join table, send to kitchen, pay, void, approve guardian) update in-memory SharedState. Table sessions are written to cr-pat-table-sessions. Menu, staff, restaurant overlays, and shifts each have their own key. KDS tickets and the guardian queue are not persisted.

Why production-complete is ~40%

That number is not “40% of the screens are done.” It answers: could a restaurant operate this product with real guests, real kitchen screens, and real colones tonight? Domain and UI are high, so the demo is strong. Backend and payments are near zero, and those two layers are what “go live” actually means. Weighting them more heavily lands around 38%, rounded to ~40%.

What is connected vs what is not

Guest, server, KDS, cashier, and admin are wired together only while they share one GuestProvider instance. Open kitchen on a second phone and it will not see the order. That is the core production gap.

Persistence is incomplete even for the prototype persistSessions() runs on send-to-kitchen, staff send, reset, and updateSession (join, cart, pay, present bill). It does not run on guest cancel, staff void, cart remove, guardian approve/reject, or KDS advance/bump. Refresh can resurrect voided items. KDS and guardian state always reset on reload.

Security blockers before any real restaurant

Must not ship

  • Plaintext 4-digit PINs in localStorage (demo PIN 0000 for manager).
  • Fake BAC API key field labeled sk_live_bac_… in settings.
  • CardDetails type (PAN/CVV) — never collect cards in the PWA.
  • Unauthenticated /kds/* and PortalSwitcher in production builds.

Must add on the server

  • Signed QR: restaurantId + tableId + rotating nonce, not guessable /m/7.
  • Server-authoritative prices (never trust client unitPrice).
  • Optimistic concurrency on table session version for split pay.
  • PCI via PSP hosted fields / wallets only; SINPE confirmation codes server-side.

Recommended backend shape

Keep the existing TypeScript domain (billing.ts, guardian.ts, kds.ts, tax.ts, order.ts) as shared packages. Replace GuestContext mutations with a thin API client + WebSocket. Do not rewrite the UI first.

Suggested stack TypeScript API (Fastify or NestJS) + PostgreSQL + Redis pub/sub + WebSockets. Object storage for menu photos. PSP for Apple/Google/card (BAC / CyberSource or equivalent CR acquirer). Separate worker for Hacienda DGT XML v4.4. One tenant = one restaurant row; never share catalogs across restaurants.

Frontend extraction (do this before writing routes)

Introduce a TableOps interface with the same methods GuestContext already exposes (joinTable, sendToKitchen, recordPayment, …). Today implement it with the current React state. Tomorrow swap in HTTP+WS without rewriting MenuScreen or FloorPlan.

Path to 100% complete

Do not treat “add a backend” as one task. Ship in this order so the restaurant can run table 7 for real, then scale to the 16-table floor.

  1. P0 Extract TableOps from GuestContext; persist every mutation; storage event or BroadcastChannel so two tabs stay in sync (proves the contract).
  2. P0 One table source of truth: catalog drives floor + QR + cashier. Remove FLOOR_TABLES vs MOCK_TABLES split. Scope menu/staff/sessions by restaurantId.
  3. P0 Real auth: hashed staff PINs, manager JWT, no PortalSwitcher in prod, KDS/cashier require a station session.
  4. P0 Signed QR tokens + BrowserRouter on HTTPS. Guest cannot guess another table. Bind menu access to sessionId server-side.
  5. P1 Postgres + REST for sessions/orders/KDS/guardian. WebSocket fan-out to guest phones, floor tablet, kitchen, bar, caja.
  6. P1 Payment intents: wallets + card via PSP (never PAN in app). SINPE Móvil as a first-class tender with reference verification. Store tax lines + tip + comprobante number.
  7. P1 Hacienda DGT XML v4.4 worker (FE/TE, cédula jurídica). Persist settings for real; send WhatsApp/email receipts from flags.
  8. P2 Full floor (all catalog tables), Z-report from ledger not table 7, live-only analytics, 86’ing items, image CDN.
  9. P2 Real PWA: web app manifest, service worker for menu shell, offline “reconnect” banner, printer/cash drawer at caja.
  10. P3 True multi-tenant (many restaurants), station pairing codes, audit log, refunds/voids on paid cycles, load tests for concurrent split pay.

What not to do

Keep GuestContext as the contract

  • Do not bolt a generic CRUD backend onto the current screens without extracting TableOps. GuestContext will stay the source of truth and the API will drift.

Stay out of PCI scope

  • Do not collect card numbers in CheckoutModal to “finish payments.” That would make the app PCI-scope overnight.
  • Do not keep HashRouter + public /m/:tableId once real money moves. Table IDs are currently guessable.
